## 1. 先给结论

如果只看论文，LingBot-VA 容易被理解成一个“视频流 + 动作流”的双流 MoT 架构：

- 视频流是大模型主干
- 动作流是更小的独立主干
- 每层各自做 QKV，再通过跨模态注意力融合

但当前 `wan_va/modules/model.py` **并不是这个结构**。

当前代码真正实现的是一种更接近下面这个形式的架构：

1. 视频 token 和动作 token 先分别做输入投影
2. 然后进入 **同一套 hidden size、同一套 Transformer blocks**
3. 文本条件也通过同一套 block 的 cross-attention 注入
4. 最后再从同一个主干里分出视频输出头和动作输出头

所以它不是论文里那种严格意义上的“分体式双流主干”，而是：

**共享主干的统一 Transformer + 模态专用输入/输出头 + 因果掩码控制的视频/动作关系**

如果要给这份代码起一个更准确的名字，我会叫它：

**单主干、统一时序、轻分支的非分体式视频-动作架构**

## 2. 论文里说的是什么架构

论文在方法部分给了两个层面的描述。

### 2.1 概念层面：两阶段

论文第 3.2 节把任务写成两步：

1. 先做视觉动力学预测，预测未来视觉状态
2. 再做 inverse dynamics，根据状态转移解码动作

这是一种“概念上分两阶段”的表述。

### 2.2 实现层面：双流 MoT

论文第 3.3 节的架构描述更具体，核心点有：

- 有一个 video stream
- 有一个 action stream
- 两个 stream 深度相同，但宽度不同
- 视频流宽度 `d_v` 大，动作流宽度 `d_a` 小，且 `d_a << d_v`
- 每层里视频和动作各自有独立的 QKV 投影和 transformer block
- 再通过 Mixture-of-Transformers / cross-modal attention 融合

论文第 4.2 节甚至给了明确配置：

- 视频流 `d_v = 3072`
- 动作流 `d_a = 768`

也就是说，**论文描述的是一个真正的双主干、非等宽、层内再融合的架构**。

## 3. 当前代码实际实现的架构

### 3.1 只有一个统一的 hidden size

`wan_va/modules/model.py` 中，模型宽度由下面这行统一决定：

```python
inner_dim = num_attention_heads * attention_head_dim
```

随后：

- 视频 patch token 通过 `self.patch_embedding_mlp` 映射到 `inner_dim`
- 动作 token 通过 `self.action_embedder` 映射到 **同一个** `inner_dim`

对应代码位置：

- `wan_va/modules/model.py:762-768`

这意味着：

- 动作分支没有单独的小宽度 latent space
- 也没有论文里 `d_v` 和 `d_a` 两套不同 hidden size

### 3.2 只有一套 Transformer blocks

当前模型主干定义是：

```python
self.blocks = nn.ModuleList([
    WanTransformerBlock(inner_dim, ...)
    for _ in range(num_layers)
])
```

对应代码位置：

- `wan_va/modules/model.py:778-785`

注意这里没有：

- `video_blocks`
- `action_blocks`
- 双流 block 对
- 每层视频流/动作流单独更新后再融合的结构

也就是说，**视频 token 和动作 token 经过的是同一套 block 参数**。

### 3.3 每个 block 也不是双流 MoT block

`WanTransformerBlock` 的结构很直接：

1. 一个 self-attention
2. 一个 text cross-attention
3. 一个 FFN

对应代码位置：

- `wan_va/modules/model.py:621-700`

这里没有论文所说的：

- 视频流自有 QKV
- 动作流自有 QKV
- 动作先升维到视频维度再做 joint attention
- 再投回动作维度

当前 block 的真实逻辑是：

**把进入该 block 的所有 token 一起送进同一个 self-attention**。

模态之间的交互，不是通过“两个 block 之间的融合层”实现的，而是通过：

- 它们先被映射到同一个 hidden size
- 再在同一个 self-attention 里直接交互

所以这更像：

**token 级统一建模**

而不是：

**双流 backbone 级融合**

### 3.4 输出是双头，但主干不是双流

模型最后确实保留了两个输出头：

- `self.proj_out`：视频输出头
- `self.action_proj_out`：动作输出头

对应代码位置：

- `wan_va/modules/model.py:787-792`

所以当前代码的“分支”主要只存在于：

- 输入头
- 部分条件嵌入
- 输出头

而 **中间最重的 Transformer 主体是共享的**。

## 4. 为什么我说它是“非分体式”

这里的“非分体式”，不是说视频和动作完全没有区分，而是说：

**它们没有被拆成两套真正独立的主干网络。**

具体证据有四个。

### 4.1 训练时四段 token 直接拼到同一个序列里

`forward_train()` 里先得到四段 hidden states：

- noisy video
- condition video
- noisy action
- condition action

然后直接：

```python
hidden_states = torch.cat([
    latent_hidden_states,
    condition_latent_hidden_states,
    action_hidden_states,
    condition_action_hidden_states
], dim=1)
```

对应代码位置：

- `wan_va/modules/model.py:853-865`

这一步非常关键，因为它说明训练时不是：

- 视频流走一套 backbone
- 动作流走另一套 backbone

而是：

- 所有 token 进入一个统一主干

### 4.2 位置编码也是统一建模

训练时会把视频和动作的 `grid_id` 拼到一起：

```python
full_grid_id = torch.cat([latent_grid_id] * 2 + [action_grid_id] * 2, dim=2)
rotary_emb = self.rope(full_grid_id)
```

对应代码位置：

- `wan_va/modules/model.py:868-872`

也就是说，RoPE 不是“视频一套、动作一套、层内再对齐”，而是：

- 在一个统一的 token 坐标体系里同时编码视频和动作

### 4.3 时间调制也是在统一主干里做的

视频和动作虽然分别算时间嵌入，但最终还是拼回一个共同的 `temb / timestep_proj`，然后喂给同一批 `blocks`：

- `wan_va/modules/model.py:874-891`
- `wan_va/modules/model.py:937-944`

这意味着时间条件的作用方式也不是两套主干独立调制，而是：

- 在共享 block 内按 token 位置施加调制

### 4.4 loss 也是一次前向同时产出两路结果

训练入口 `wan_va/train.py` 中：

```python
output = self.transformer(input_dict, train_mode=True)
latent_loss, action_loss = self.compute_loss(input_dict, output)
loss = latent_loss + action_loss
```

对应代码位置：

- `wan_va/train.py:339-343`

说明训练范式是：

- 一次统一前向
- 同时得到视频预测和动作预测
- 再分别算两项 loss

这也更符合“非分体式共享主干”的定义。

## 5. 训练时它其实是怎样把视频和动作组织起来的

这部分是理解当前实现最关键的地方。

### 5.1 它不是字面上的交错拼接

论文常见的直觉图是：

```text
[z_t, a_t, z_{t+1}, a_{t+1}, ...]
```

但当前代码训练时 **不是按这个物理顺序直接拼接**，而是先按块拼成：

```text
[noisy_video | cond_video | noisy_action | cond_action]
```

也就是：

- 先放一整段视频 noisy token
- 再放一整段视频 condition token
- 再放一整段动作 noisy token
- 再放一整段动作 condition token

### 5.2 真正的“交错时序关系”是靠 mask 和 frame id 实现的

`_build_joint_token_metadata()` 会给视频和动作 token 人为构造交错的 `frame_id`：

- 视频 frame id 编成偶数：`0, 2, 4, ...`
- 动作 frame id 编成奇数：`1, 3, 5, ...`

对应代码位置：

- `wan_va/modules/model.py:52-91`

动作 token 的 `get_mesh_id(..., action=True)` 还会把动作放到同一条时间轴上，只是不再给真实二维空间坐标：

- `wan_va/utils/utils.py:33-53`

因此，当前实现的“统一序列”更准确地说是：

**物理存储上分块拼接，时序语义上用 frame id 和 attention mask 做交错统一**

这和论文图示的“直接交织 token 顺序”不是一回事。

## 6. 当前代码虽然是非分体式，但并不是完全对称的联合生成

这一点非常重要。

很多人看到“统一主干”就会以为视频和动作在代码里是完全对称、同时互相预测的。其实不是。

### 6.1 训练 mask 明确保留了“先视频、后动作”的方向性

训练用到的 mask 规则主要有三条：

- `clean -> clean`：只能看当前及过去
- `noise -> clean`：只能看严格过去
- `noise -> noise`：只能看同一 frame

对应代码位置：

- `wan_va/modules/model.py:102-152`
- `wan_va/modules/model.py:264-319`

再结合偶数/奇数 frame id，可以得到一个非常关键的结果：

1. 当前 noisy 视频 token 只能看到过去的 clean 视频/动作，**看不到同一 chunk 的动作**
2. 当前 noisy 动作 token 可以看到同一 chunk 的 clean 视频，因为视频 frame id 比动作早一个位置

这意味着训练时实际学到的是一种带方向性的关系：

- 视频分支更像 forward dynamics，依赖历史
- 动作分支更像 inverse dynamics，可以利用当前 chunk 的视频状态

所以当前实现虽然是“统一主干”，但它并不是“完全对称的 joint denoising”。

### 6.2 推理时更明显：先生成视频，再生成动作

`wan_va/wan_va_server.py` 的 `_infer()` 非常清楚地写成了两段：

1. 先跑视频 diffusion loop
2. 再跑动作 diffusion loop

对应代码位置：

- 视频生成：`wan_va/wan_va_server.py:487-521`
- 动作生成：`wan_va/wan_va_server.py:523-560`

并且视频最后一步会先把预测视频写入 KV cache：

- `update_cache=1 if last_step else 0`

随后动作生成再读取这个 cache。

因此推理阶段的真实调用顺序其实是：

```text
历史观测/历史动作
  -> 先预测当前 chunk 视频
  -> 把预测视频写入 cache
  -> 再预测当前 chunk 动作
```

这和论文第 3.2 节里的“先视觉动力学、再 inverse dynamics”其实反而是高度一致的。

所以更准确的说法是：

**当前代码在参数结构上是非分体式单主干，但在信息流方向上仍然保留了明显的两阶段非对称性。**

## 7. 推理时为什么看起来又像“分开调用”

这也是最容易让人误判的地方。

`WanTransformer3DModel.forward()` 在推理态有一个 `action_mode`：

- `action_mode=False` 时走视频输入头和视频输出头
- `action_mode=True` 时走动作输入头和动作输出头

对应代码位置：

- `wan_va/modules/model.py:965-1049`

这会给人一种“视频模型”和“动作模型”分开的印象。

但实际上，这只是：

- **同一个主干网络**
- 在不同输入/输出头配置下
- 被调用了两次

共享的东西仍然是最核心的部分：

- `self.blocks`
- `self.norm_out`
- `self.scale_shift_table`
- self-attention 参数
- 文本 cross-attention 参数

所以这里的“分开调用”不等于“分体式双模型”，而是：

**单模型的两种工作模式**

## 8. 论文与代码最关键的不一致点

下面这张表可以直接概括差异。

| 项目 | 论文描述 | 当前代码实际实现 |
| --- | --- | --- |
| 主干数量 | 双流主干：video stream + action stream | 单主干：一套 `self.blocks` |
| 主干宽度 | 非等宽，`d_v >> d_a` | 单一 `inner_dim`，视频动作同宽 |
| 每层结构 | MoT，视频/动作各自 block 后再融合 | 一个 block 直接处理所有 token |
| QKV 参数 | 两个 stream 各自独立 QKV | 一套 self-attention QKV |
| 融合方式 | cross-modal fusion / MoT | 统一 hidden space 中直接 self-attention |
| 训练序列 | 论文图示强调交错 unified sequence | 实现上是四段拼接 + mask 交错时序 |
| 推理方式 | 论文叙述上联合 video-action world modeling | 代码里明确先视频、后动作，两次调用同一主干 |

## 9. 这份代码应该怎样被准确描述

如果要避免把当前实现误写成论文里的双流 MoT，我建议用下面这段话描述：

> 当前 `wan_va/modules/model.py` 实现的不是论文中严格意义上的双流 Mixture-of-Transformers，而是一个共享 Transformer 主干的统一视频-动作模型。视频 latent token 与动作 token 先通过各自输入头投影到同一 hidden space，再在同一套 Transformer blocks 中通过统一的 self-attention 和因果 mask 建模跨模态关系，最后分别由视频头和动作头解码。训练阶段通过四段 token 拼接和 frame-aware mask 实现统一 teacher forcing；推理阶段则复用同一主干，按“先视频、后动作”的顺序滚动生成并结合 KV cache 维持历史上下文。

如果再压缩成一句话：

> **这是“共享主干的统一视频-动作 Transformer”，不是“两个 backbone 并行再融合”的分体式 MoT。**

## 10. 一个更贴近代码的结构图

```text
video latent -----------------> patch_embedding_mlp ---\
                                                        \
action token -----------------> action_embedder ---------> shared Transformer blocks ---> proj_out --------> video prediction
                                                        /
text embedding ----------------> cross attention -------/                               ---> action_proj_out -> action prediction

time / timestep ---------------------------------------> AdaLN-style modulation
RoPE / grid_id ---------------------------------------> shared positional encoding
```

训练时：

```text
[noisy_video | cond_video | noisy_action | cond_action]
                 |
                 v
           shared blocks
                 |
        +--------+--------+
        |                 |
     video head       action head
```

推理时：

```text
历史 cache -> 先生成视频 chunk -> 写入 cache -> 再生成动作 chunk
```

## 12. 最终总结

从论文到代码，真正发生的变化可以概括为：

1. 论文强调的是“概念上两阶段 + 架构上双流 MoT”
2. 当前代码落地成了“参数上单主干共享 + 调用上分视频/动作模式”
3. 训练时通过统一序列和因果 mask 把视频/动作放进同一个 Transformer
4. 推理时又保留了“先视频、后动作”的非对称顺序

所以，如果你要解释当前 `model.py` 的架构，最准确的说法不是：

- “论文里的双流 MoT 已经完全实现”

而应该是：

- **代码把论文里的双流构想收缩成了一个统一 hidden space 的单主干实现**
- **它保留了世界模型先预测视觉、再解码动作的方向性**
- **但没有保留论文里那种真正独立的 video/action 双 backbone 设计**
